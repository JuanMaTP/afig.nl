# AFiG website

Website for **AFiG: Amsterdam Film Group**, a community-focused film meetup in Amsterdam: *community first, films second, with a strong preference for interesting cinema.* A Dutch community that happens to be international. About 1,270 Meetup members; roughly ten events every two weeks.

Built by the organizer and a second host, with Claude. **Built so far (2 October 2026):** the Meetup ingest, the agenda (list and month views), `/calendar.ics`, and the archive at `/past` with all past events backfilled; on 3 October, film matching against TMDB in the cron (table `films`, migration `0005`), and the screening search (plan §5.7): a daily cinema run (Eye, LAB111, De Uitkijk, Studio/K, Het Ketelhuis, Cinecenter, Rialto De Pijp, FC Hyena, Cinema De Vlugt, Melkweg, The Pulse and Filmhuis Cavia) and the pages `/films` and `/films/<TMDB id>`; on 4 October, member sign-in with Google (Better Auth, migration `0008`, `/sign-in`), `/films` open only to members who sign in, **Recommend** (`/recommend`, plan §5.3, migration `0009`): members who sign in recommend films and send screenings they spotted, which only the hosts see, and the hosts read them in the **host tools** (`/hosts`, plan §5.9), open to members whose email is in the secret `HOST_EMAILS`; and the navigation by category, a sidebar on wide screens and a Menu on phones: **The group** (Events, with views Upcoming `/`, Calendar `/calendar`, Past `/past`; About) · **Tools** (Film finder `/films`, Recommend) · **Hosts** (hosts only), with the account and Sign out. **Every page in the menu is listed once, under its category, in `src/lib/navigation.ts`** (`docs/brand/design-direction.md`, Navigation and account). **Live on https://afig.nl since 2 October 2026:** the Worker `afig-website` (custom domain `afig.nl`), the EU D1 (`afig-website`, migrations applied) and the cron, deployed by hand with `npm run build` then `npx wrangler deploy`. On 4 October production got migrations `0005`–`0008` and its secrets (`TMDB_TOKEN`, `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`); before that, film matching and the cinema run had never run there (plan §8). Workers Builds isn't connected yet. Both domains are on Cloudflare (free plan).

## Stack (decided 30 September 2026, reviewed 1 October 2026)

**Astro 7.3.x** + **`@astrojs/cloudflare` 14.x** (pin both) + TypeScript on **Cloudflare Workers** (Workers Paid plan, $5/month) · **D1** (SQLite, created with `--jurisdiction=eu`; previews get their own) · **Cron Triggers** in the same Worker (`src/worker.ts`, ingest every 30 min; cinema reads once a day, moving to **Workflows** when they outgrow one run) · **linkedom** for cinema pages (approved, installed with the first reader) · **Drizzle ORM** 0.45 · plain forms posted to their own page for members who sign in, **Astro Actions** + **Turnstile** for forms open to visitors · hosts as members with a **host role** (`HOST_EMAILS`) for the host tools at `/hosts` (Cloudflare Access on `/admin` was the plan until 4 October 2026) · **Cloudflare Web Analytics** · fonts self-hosted with Astro's Fonts API · **Healthchecks.io** watching the cron · **Vitest 4.1** + `@cloudflare/vitest-plugin` · **GitHub** (private, `JuanMaTP`) + **Workers Builds**. Member sign-in (from 4 October 2026): **Better Auth** 1.7.7 (Google, then email links through **Brevo**; Drizzle adapter, `src/lib/auth.ts`). Film data: **TMDB API**. Details and reasons: `docs/website-plan.md` §9.

## Rules

- **Never show a guessed screening detail.** If a field can't be read reliably, leave it out or show the Meetup description.
- **Hosts publish once, on Meetup.** Never add a step that makes a host enter data twice.
- **Meetup source:** the group's events page `https://www.meetup.com/amsterdam-film-group/events/?type=upcoming` (structured data in its `__NEXT_DATA__` block, all upcoming events, number going, RSVP limit, cover image). Fallback: the iCal feed `…/events/ical/` (next 10 events only). **Never** use the RSS feed (robots.txt disallows it) or Meetup's internal APIs (`/gql*`, `/api/`).
- **Discard personal data** embedded in Meetup pages: attendees, creator, hosts. The site shows "13 going", never who.
- **Meetup time and film start are separate fields.** Never conflate them (people have arrived an hour early).
- **Language and subtitles are prominent** on every event. For most members it decides whether they come.
- **Descriptions vary by host.** Parse leniently; accept label variants (`Auditorium:` / `Theater:` / `Zaal:`, `Film starts:` / "The film starts at"). Hosts were asked to include four labeled lines: `Film starts:` · `Tickets:` · `Language:` · `Auditorium:`.
- **Film matching:** clean event titles with `EK` from the Film Group project's `claude/AFG-Matcher.md` §2. **Copy it verbatim, never retype it** (retyping caused three bugs in that code's history). Look films up on TMDB by **title + year + director**; accept only confident matches (the rule: plan §8, "Film matching for events"; the code: `src/lib/films/`). `EK` cuts off titles containing "with" or a language word (*The English Patient* → `the`), so never match on the cleaned title alone. A missing poster is fine, a wrong one is not.
- **Film identity:** every film has the site's own id (`films.id`), which other tables reference. TMDB is its identity and the source of its data, as **kind + id** (TMDB numbers films and series separately), unique together; the IMDb id is a unique cross-reference. **Never use IMDb's data or read imdb.com**, its datasets included: its `robots.txt` and Conditions of Use forbid it. IMDb ids come from TMDB or from a member's own export (plan §4, §8).
- **Cinema reads** (plan §5.7, §9): check each site's terms and `robots.txt` before its reader is built; honour `Crawl-delay`; one request at a time per site; never work around bot protection. Ticket sites often disallow every robot: link to them, never fetch them. A film counts as screening only with a date still ahead. **Personal data never goes through Workflows** (no EU jurisdiction).
- **Venues:** map Meetup venue ids through the `venues` aliases. Meetup has the same cinema under several ids (LAB111 under three).
- **D1 must be created with the EU jurisdiction.** It can't be added later. Previews bind their own D1 (also EU); a preview must never reach the production database. Keep the placeholder `database_id` in `wrangler.jsonc` until the EU database exists: without an id, `wrangler deploy` creates a database itself, outside the EU.
- **D1 migrations:** `drizzle-kit generate`, then `wrangler d1 migrations apply`; no other migrator. Check every migration that rebuilds a table: D1 enforces foreign keys and the rebuild silently deletes child rows (Drizzle #5782). Use `PRAGMA defer_foreign_keys = on`.
- **Admin security:** hosts are members with a host role (plan §8, 4 October 2026): `Astro.locals.member()` gives `host: true` only for a verified email in the secret `HOST_EMAILS`. **Every host page, endpoint and Action checks `member.host` itself, on the server, before it reads or writes anything**, and answers 404 to anyone else; `src/layouts/Hosts.astro` protects nothing. Astro serves every Action at `/_actions/<name>`, so an Action can't rely on a page's check. Host pages are never prerendered. `workers_dev = false`.
- **Secrets** (the TMDB token as `TMDB_TOKEN`; `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` for sign-in; `HOST_EMAILS`, the hosts' sign-in emails separated by commas; later the email key) live in Cloudflare's secret store, never in the repo; locally in `.dev.vars`, which git ignores. Without `HOST_EMAILS` nobody is a host.
- **Bindings:** `import { env } from "cloudflare:workers"`. `Astro.locals.runtime` no longer exists; follow docs.astro.build, not Cloudflare's own Astro guide, which is out of date.
- **Keep Cloudflare-specific code** (bindings, Access, cron) in one small module, so the app stays portable.
- **TMDB attribution** in About/Credits, in the binding wording of TMDB's Terms §3: "This website uses TMDB and the TMDB APIs but is not endorsed, certified, or otherwise approved by TMDB." plus the TMDB logo, less prominent than our branding. **Refresh `films` rows before they are six months old**; the Terms forbid keeping TMDB data longer. The key is on TMDB's free, non-commercial Developer plan, so **the site earns no money while it uses TMDB data** (no ads, sponsorship, ticket sales or affiliate links) without a commercial agreement with TMDB first (plan §4, §8).
- **Name:** the name is **AFiG**; "Amsterdam Film Group" is its subtitle, and in many places follows it: "AFiG: Amsterdam Film Group" (the site's header, page titles, link previews, the calendar's name). No "The", lowercase *i*. Public-facing text outside the site keeps "Amsterdam Film Group" until AFiG is announced (preferred: together with the site launch). The site itself goes public as soon as it is deployed, before the announcement (decided 2 October 2026, plan §8).
- **Mobile first** (members arrive from WhatsApp links), **English**, **community first**.
- **The WhatsApp invite link stays off the public site.**

## Working agreements

- **Claude never commits or pushes**, on either computer or from the chat. The organizer reviews and commits every change. Claude leaves changes in the working tree, can propose a commit message, and reminds the organizer to commit and push before switching computers. Enforced on both computers by `.claude/settings.json` (deny rules) and the hook `.claude/hooks/block-git-writes.mjs`, which works in every permission mode. The same file makes `npm install`, deploys, secrets and remote D1 commands always ask first.
- **Claude never deploys or changes production**: no `wrangler deploy`, no secrets, no writes to the remote D1 (migrations, imports, executes), no rollbacks. The organizer runs them, unless they give permission for that step at that moment; "let's deploy" is not that permission. Claude prepares the exact commands, in order, and hands them over. Enforced by the hook `.claude/hooks/ask-before-production.mjs`, which asks even when the command is chained or piped (the `ask` rules in `.claude/settings.json` only match a command by how it starts; that gap let a deploy through on 4 October 2026).
- Pull before you start; commit and push before switching computers. Once Workers Builds is connected, `main` is production: push a branch, never `main` (`docs/engineering.md`, Git and commits).
- **Speed first, without dead ends.** Before launch, follow `docs/engineering.md` "Launch mode": logic out of the entrypoints, external data validated with `astro/zod`, tests where a mistake reaches members, shortcuts marked `// TODO(after-launch): …`.
- **Conventional Commits** (`feat(agenda): …`). Claude proposes messages in that form.
- Record decisions in `docs/website-plan.md` §8, not only in chat.
- **Meetup from Cloudflare works** (confirmed 2 October 2026): the deployed cron read the events page and stored all 14 upcoming events. The GitHub Action fallback isn't needed.

## Commands

- `npm run dev`: local dev server (workerd, through the Cloudflare Vite plugin). Regenerates binding types first.
- `npm run build`, then `npm run preview`: the production build, served locally in workerd.
- Trigger the cron locally while dev or preview runs: `curl "http://localhost:<port>/cdn-cgi/local/scheduled?cron=*/30+*+*+*+*"` (the Meetup ingest, then film matching); the daily cinema run is `?cron=15+4+*+*+*` (about 5 minutes: Eye is the slowest). Both need `TMDB_TOKEN` in `.dev.vars` to match films.
- `npm run check`: type-check (`astro check`).
- `npm test`: Vitest, in two projects: `unit` (plain modules, in Node) and `workers` (the ingest and D1, in Cloudflare's runtime, under `test/workers/`).
- `npm run db:generate`, then `npm run db:migrate:local`: Drizzle migrations into the local D1. Check every generated migration first (Rules, D1 migrations).
- **The local agenda:** on a fresh clone, run `npm run db:migrate:local` once, then trigger the cron while dev runs. The agenda shows whatever the last run stored. **Run `npm run db:migrate:local` again after pulling new migrations** (with dev stopped): the archive's events and venues arrive that way.
- **The archive backfill** (`scripts/backfill/`, plan §5.2) was a one-time job, done 2 October 2026. Its migrations are `0002` and `0003`; don't regenerate them. The tools stay for a re-run if Meetup's history ever needs reading again.
- **Local D1 answers every query with "internal error; reference = …":** its WAL index went stale (seen 2 October 2026, after a dev server was stopped abruptly). Stop dev, then in `.wrangler/state/v3/d1/miniflare-D1DatabaseObject/` delete the `.sqlite-shm` and `.sqlite-wal` next to the database, **only if the `-wal` is 0 bytes** (a non-empty one holds unsaved writes). The data is in the `.sqlite` file and stays.
- **Local agenda fails with "Failed query … no such table" after a pull:** the local D1 lives in a file named after `database_id` in `wrangler.jsonc`, so a new id starts an empty local database (happened 2 October 2026, when the placeholder became the real EU id). Stop dev, run `npm run db:migrate:local`, start dev and trigger the cron. The old file can be deleted.

The entrypoint is `src/worker.ts`: Astro's `handle()` for requests, `scheduled()` for the ingest. A site with only prerendered pages builds no Worker at all, so the cron needs at least one on-demand route.
